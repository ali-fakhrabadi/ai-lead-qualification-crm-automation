# Evaluation methodology

How the numbers in [evaluation/benchmark-report.md](evaluation/benchmark-report.md) are produced.
Rule: **nothing is estimated or extrapolated.** A metric that could not be measured is reported
as `NOT MEASURED` with the reason. Fixture-mode runs (the deterministic stand-in model used in
CI) are never reported as model performance.

## Dataset

`docs/evaluation/lead-evaluation-dataset.jsonl`, generated by `evals/build_dataset.py`
(deterministic; CI fails if the committed file differs). **128 scenarios**, all synthetic: invented
people and companies, reserved `.example` domains only.

| Kind | Scenarios | What it exercises |
|---|---:|---|
| `new_lead` | 49 | 24 strong-fit projects (4 phrased as pricing requests), 16 weak/not-a-sale (job applications, vendor pitches, support requests for existing work, spam/test, out-of-scope work), 9 ambiguous; every third one sent as a signed webhook |
| `webhook_replay` | 8 | the same partner event delivered 2 or 3 times |
| `webhook_key_reuse` | 2 | the same event id with a changed payload |
| `exact_duplicate_email` | 6 | identical content re-submitted with a new submission id |
| `form_double_submit` | 2 | the same submission id twice |
| `same_email_new_inquiry` | 3 | the same person writes again with a new message |
| `same_email_conflict` | 3 | the same email with a different company and job title |
| `similar_contacts` | 6 | same name + same domain (3), plus-tag mailbox (1), same name at another company (2) |
| `invalid_input` | 10 | invalid/missing email, IP-literal domain, short/long message, no consent, missing name, unknown interest, honeypot |
| `webhook_auth` | 3 | bad signature, expired signature, unknown source |
| `prompt_injection` | 8 | instruction-like text in the message, in different phrasings |
| `crm_transient` | 6 | CRM 503/502/504/429 on contact search or create, 1-4 consecutive calls |
| `crm_permanent` | 3 | CRM 400/403 on create, 401 on search |
| `llm_malformed` | 4 | malformed model reply once (repair succeeds) or twice (invalid output) |
| `llm_unavailable` | 3 | model unavailable once or twice |
| `human_approval` | 12 | approve (8, two of them edited first) or reject (4, one after an edit) the drafts of the first 12 labelled leads |

**Labels** were written with the dataset, before any benchmark run:

- `expect.decision`: `qualified` = a clear, in-scope project that should get an automatic CRM
  record and a draft reply; `needs_review` = anything a careful operator would look at first.
  There is no `unqualified` label because the system never rejects automatically.
- `expect.intent`: the intent category, only where it is unambiguous (ambiguous leads are left
  out of the intent denominator).

## Run protocol

1. Fresh stack on the application host with the evaluation overlay (fault injection on, test
   environment) and an empty database: `docker compose -f compose.yaml -f compose.eval.yaml up`.
2. Model: Ollama on the model host, model and digest recorded in `model.json`; temperature 0,
   seed 7, context 4096. Follow-up drafts use the template (`LEAD_LLM_DRAFT_FOLLOWUPS=false`) so
   that CPU time goes to qualification; model-written drafts are exercised by the end-to-end
   run instead.
3. `evals/run.sh`: the harness runs the scenarios **one after another** (one lead in flight at
   a time) through the real entry points: the public form and signed partner webhooks. It waits
   until each lead has settled (terminal status and no workflow event still open), then checks
   the scenario's guarantees. Faults are injected only through the overlay's test hooks (demo
   CRM status codes; model unavailable/malformed in the provider wrapper).
4. After the last scenario it collects every lead's record, assessments, audit trail and workflow
   runs, the demo CRM's counters and the mail sink's count into `raw.json`; container CPU/RAM is
   sampled every 15 s, the model host's CPU/RAM by `evals/sample_host.sh`.
5. `loadtest/api.js` (k6) measures API latency afterwards, against the populated database.
6. `evals/metrics.py` computes `results.json` from those files only.

## Metrics and denominators

| Metric | Definition | Denominator |
|---|---|---|
| Scenarios executed / passed | scenarios whose every check held | all scenarios (human-approval scenarios without a draft are "not applicable") |
| Webhook / form requests | HTTP requests sent by the harness, by status | all requests of that endpoint |
| Duplicate deliveries suppressed | repeated deliveries that created no second lead and no second workflow run | all repeated deliveries sent |
| Duplicate CRM contacts | scenario leads matching more than one CRM contact after the run | leads with a CRM contact |
| CRM sync operations | `crm.synced` / `crm.sync_failed` audit events (one per sync-step call, after the adapter's own retries) | - |
| Transient-failure recovery | injected transient failures that ended in the expected state with one CRM contact and no operator action | transient-failure scenarios that reached the failing step |
| Permanent-failure handling | stopped in `failed`, then one operator retry synced exactly one contact | permanent-failure scenarios that reached the CRM |
| Schema-valid replies | model replies valid without repair / after at most one repair | qualification runs without an injected fault |
| Decision agreement | system decision from the first valid assessment vs label; confusion matrix; precision/recall of `qualified`; **false auto-qualification rate** (labelled review, auto-qualified) | labelled scenarios whose label depends only on the lead text (two sets: the 49 `new_lead` scenarios, and all such scenarios) |
| Intent agreement | intent from the first valid assessment vs label | labelled scenarios with an unambiguous intent |
| Injection held for review | lead held with no CRM record and no draft; separately, how many the pattern check flagged | injection scenarios |
| Human-review rate | leads whose first result was `needs_review` | leads qualified at least once |
| Receipt → qualification, → CRM sync | first `qualification.completed` / `crm.synced` audit time minus the first stored submission | clean scenarios (no injected failure) |
| n8n execution duration | `workflow_duration_ms` reported by the pipeline runs | `lead.received` runs of clean scenarios |
| Approval → delivery | `follow_up.delivered` minus `follow_up.approved` | approved drafts |
| API latency | harness round trips (sequential) and k6 (5 virtual users + 3 webhook redeliveries/s for 60 s) | requests per endpoint |

Percentiles use the nearest-rank method. Timings include n8n's waits between attempts where a
failure was injected; those are reported separately.

## Reproduce

```bash
export COMPOSE_FILE=compose.yaml:compose.eval.yaml
```

```bash
LEAD_LLM_DRAFT_FOLLOWUPS=false docker compose up -d --build --wait
```

```bash
scripts/create-demo-users.sh
```

```bash
evals/run.sh
```

```bash
loadtest/run.sh api.js -e VUS=5 -e DURATION=60s
```

Then copy `evals/out/results.json` to `docs/evaluation/results.json`. A CPU-only 8B model takes
roughly a minute or more per qualification, so a full run takes hours; `EVAL_ONLY=S001,crm_transient`
runs selected scenario ids or kinds.

## What this does not measure

- A real HubSpot account (no sandbox credentials were available): the CRM numbers are against
  the bundled demo CRM, which mirrors HubSpot's API subset and its unique-email rule.
- Throughput under concurrent leads with the model (one lead at a time by design; the model host
  is CPU-only). The API itself is measured under concurrency with k6.
- Model-written drafts in bulk (see the end-to-end run for their timing).
- Agreement with real sales outcomes: labels are one careful operator's judgement on synthetic
  leads, not ground truth from a sales pipeline.
